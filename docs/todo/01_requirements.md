# TODOアプリ V1 要件定義書

## 1. 目的・対象範囲

既存の Express＋TypeScript＋EJS サイトに、TODOの一覧表示・登録・完了状態の部分更新・削除を追加する。画面は `/todo`、REST API は `/api/v1/todos` とする。既存の `/` と `/api/db-check` は維持する。画面から Fetch を使用してAPIを呼び出す。

DBは学生自身の Neon PostgreSQL を使用し、既存のDB接続処理と環境変数 `DATABASE_URL` を再利用する。公開先は Vercel とし、Preview と Production は同じ Neon DB を参照する。個人情報は扱わず、架空のデータのみを使用する。

V1では、認証、優先度、絞り込み、タイトル更新を実装しない。検索条件をクエリで指定する機能はV2の検討対象とする。ブラウザ側の `TodoApi` クラスへの分割や実ファイル配置の確定は設計書で扱う（ファイル配置の一部は**要確認**）。

## 2. 機能要件と受け入れ条件

### REQ-01 TODO一覧表示

- **操作:** `/todo` を開き、画面から `GET /api/v1/todos` を実行する。
- **入力:** なし。V1では絞り込み用クエリを使用しない。
- **結果:** TODO一覧を取得し、画面に表示する。0件の場合もHTTP `200` とし、レスポンスに `data: []` を含める。GETによってDBを変更しない。
- **エラー:** DB接続・取得処理が失敗した場合は共通エラー仕様に従う。エラーJSON形式と `500` / `503` の使い分けは**要確認**。
- **受け入れ条件:** 登録済みTODOを一覧で確認できる。0件の場合は正常応答（`200`、`data: []`）となり、GETの前後で保存データが変化しない。
- **確認方法:** データがある状態・ない状態で画面表示とAPIレスポンスを確認し、GET前後のDBレコードを比較する。

### REQ-02 TODO登録

- **操作:** `/todo` 画面から新規TODOを入力し、`POST /api/v1/todos` を実行する。
- **入力:** `title`。前後の空白を除いた後の長さを1〜100文字とする。リクエストJSON形式およびその他の項目は**要確認**。
- **結果:** 条件を満たすTODOをDBに登録し、画面上で登録結果を確認できる。成功時のHTTPステータスおよびJSON形式は**要確認**。
- **エラー:** `title` が空白除去後0文字または101文字以上の場合は登録しない。`400` / `422` の割り当てとエラーJSON形式は**要確認**。DB障害は共通エラー仕様に従う。
- **受け入れ条件:** 有効なタイトルが保存され、再取得できる。空文字、空白のみ、101文字以上は保存されない。1文字および100文字は受け付ける。
- **確認方法:** 境界値（0・1・100・101文字）、前後の空白、正常入力でAPI応答・画面・DB保存結果を確認する。

### REQ-03 完了状態の部分更新

- **操作:** 対象TODOの完了状態を画面で変更し、`PATCH /api/v1/todos/:id` を実行する。
- **入力:** パスの `id` は1以上の整数。完了状態を表すJSONフィールド名、型、許容値は**要確認**（設計時に確定する）。
- **結果:** 指定した既存TODOの完了状態だけを更新し、画面に反映する。タイトルは更新しない。成功時のHTTPステータスとJSON形式は**要確認**。
- **エラー:** 不正なIDや更新値は共通入力エラー仕様に従い、存在しないIDは `404` とする。`400` / `422` の使い分けとエラーJSON形式は**要確認**。
- **受け入れ条件:** 既存のIDに対して完了状態だけが変更され、他の情報は変わらない。不正なID・不正な更新値は保存されず、存在しないIDには `404` が返る。
- **確認方法:** 存在するID、存在しないID、`0`・負数・小数・文字列のID、更新値の正常・異常ケースを確認する。更新前後のDB内容を比較する。

### REQ-04 TODO削除

- **操作:** 対象TODOの削除を画面から指示し、`DELETE /api/v1/todos/:id` を実行する。
- **入力:** パスの `id` は1以上の整数。
- **結果:** 指定した既存TODOを削除し、画面一覧に反映する。削除成功時はHTTP `204`、レスポンス本文なしとする。
- **エラー:** 不正なIDは共通入力エラー仕様に従い、存在しないIDは `404` とする。`400` / `422` の使い分けとエラーJSON形式は**要確認**。
- **受け入れ条件:** 削除後は対象TODOが一覧に表示されない。成功時のレスポンスは `204` で本文がない。同じIDへのDELETEを繰り返しても最終的に対象が存在しない状態は同じ（2回目以降の応答は未発見として `404`）。
- **確認方法:** 正常削除・再取得・同一IDの再削除・不正ID・存在しないIDを試し、HTTPステータス、本文の有無、DB状態を確認する。

## 3. 共通のデータ・API・エラー条件

APIのリソース名は名詞・複数形の `/api/v1/todos` とし、`GET`＝取得、`POST`＝作成、`PATCH`＝部分更新、`DELETE`＝削除とする。特定のTODOは `/:id` で指定する。GETはDBの状態を変更しない。DELETEは繰り返しても最終的なDB状態が同じになるようにする。

`title` は前後の空白を除いて1〜100文字、URLパスの `id` は1以上の整数である。DBテーブル名、保存カラム、完了状態の表現、日時項目、一覧の並び順、POST/PATCHのリクエスト形式は**要確認**。タイトル変更APIはV1の対象外とする。

0件のGETはHTTP `200`、`data: []`、削除成功はHTTP `204`・本文なし、存在しない対象のPATCH/DELETEはHTTP `404` とする。それ以外の成功JSONの構造、POST/PATCHの成功ステータス、エラーJSONの構造、`400`（不正リクエスト）・`422`（入力検証エラー）・`500`（内部エラー）・`503`（サービス利用不可）の具体的な判定境界は**要確認**。未確定のステータスやJSON形式を実装前に設計書で確定し、画面・API・テスト間で統一する。

## 4. 環境別確認

- **ローカル:** `DATABASE_URL` による既存DB接続を確認し、既存 `/`・`/api/db-check` と `/todo`、4つのAPI操作が動作することを確認する。テストには架空のデータのみを使う。
- **Vercel Preview:** Preview環境で既存ページとTODO画面/APIの動作を確認する。Productionと同一のNeon DBを参照するため、作成・変更・削除するテストデータを区別し、他環境のデータへの影響を確認する。
- **Vercel Production:** 公開後に既存ページとTODO画面/APIの動作を確認する。Previewと同じNeon DBを利用することを確認し、架空のテストデータのみを扱う。

**設計書での要確認事項:** ファイル配置の未確定部分、DBスキーマ、一覧順序、PATCH入力仕様、成功JSON・成功ステータス、エラーJSON・400/422/500/503の判定基準、ブラウザ側の`TodoApi`クラス構成。
