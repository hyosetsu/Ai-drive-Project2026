### 0.2 確定済みの制約

- 質問：前後空白除去後 **1〜2,000 Unicodeコードポイント**。
- JSON本文：**16,384バイト以下**。
- 履歴：**最新20件**、`created_at DESC, id DESC`。
- **AI回答取得とDB保存成功の双方が完了するまで201を返さない**。
- AIに過去履歴を送信しない。ブラウザ・SDKの自動再試行をしない。
- ローカルまたは保護済みPreviewのみでデモ、Productionで質問・履歴API停止（履歴停止は今回採用した設計判断）。
- 30秒（AI）・45秒（ブラウザ）は**参考値**であり、実測による確定が必要。
- ログイン、利用者別履歴、会話記憶、Markdown表示、ストリーミングは標準課題外。
- 今回ユーザーが指定した追加の設計前提：`/ai`、`POST /api/ai/ask` 成功201、`GET /api/ai/history` 成功200（0件は空配列）、**質問・履歴ともデモ停止503／`DEMO_DISABLED`**。これにより、従来未決であったProductionの履歴取得も**本設計では停止**する。

本書に定める**画面方式、DB構成、§4.3のHTTPステータス・エラー応答形式は採用設計として確定**する。ただし採用設計は実動作を保証するものではなく、SDK・モデルID、固定システムプロンプト、Previewの保護方式、タイムアウト最終値などは第11章の未決・検証事項として扱う。

## 1. 全体構成・処理の流れ（DES-AI-001）

```text
ブラウザ /ai (HTML, app.js)
  ├─ 起動時 GET /api/ai/history ───────────────┐
  └─ 質問 POST /api/ai/ask ───────────────────┤
                      Express (index.ts)     │
                      aiRouter内でデモ判定    │
                           ├─ aiController ──┤
                           │   ├─ aiService → Gemini API
                           │   └─ aiModel ───→ PostgreSQL (db.ts共有pool)
                           └─ JSON/404/例外処理
```

| 主体 | 責務 | 持たない責務 |
| --- | --- | --- |
| ブラウザ | UI表示、Fetch、送信中制御、描画、初期履歴取得、ユーザー操作を伴う手動再送 | Gemini APIキー保持、DB直接アクセス、AI SDK実行 |
| Express | デモ可否の判定、JSON受信、入力検証、AI→保存→応答の順序、公開用エラー変換、問い合わせID | 秘密値のクライアント送信、過去履歴のAIへの転送 |
| Gemini API | 単発質問に対する回答文字列の生成 | 履歴の永続保存、利用者識別 |
| PostgreSQL | 成功した質問・回答の**同一レコード**保存、最新20件の安定順取得 | 外部AI生成、画面描画 |

### 1.1 シーケンス（成功）

1. ブラウザが `/ai` を開く。画面は静的HTMLを読込み、`GET /api/ai/history` を**1回**実行する。
2. 利用者が質問を入力し送信する。ブラウザは送信中表示とボタン無効化を行い、**1回** `POST /api/ai/ask` を送る。
3. Expressは先にデモ許可を判定し、JSON本文サイズ・構文・Content-Type・質問型・トリム後のコードポイント数を検証する。
4. ControllerがServiceに**今回の質問だけ**を渡し、ServiceがGemini APIから非空回答を取得する。
5. ControllerがModelに質問・回答を渡し、**1レコードのINSERTが成功した後**、`201 Created` と保存済みデータを返す。
6. ブラウザは回答を平文表示し、成功後に履歴を再取得して表示する。履歴の再取得失敗は**質問保存成功を取り消さず**別の履歴エラーとして示す。

**部分成功の考え方：** Gemini応答取得だけでは成功ではない。INSERTが失敗したら成功レスポンスを返さない。INSERT後の通信断などでクライアントが結果を受信できなかったケースは「結果不明」とし、後述のOPEN-AI-07で扱う。

## 3. 画面設計と状態遷移（DES-AI-003）

### 3.1 `/ai` の主要要素

| 要素 | 役割と表示ルール |
| --- | --- |
| `h1`・TOP/TODOへのリンク | AI質問ページを識別し既存画面へ移動。TOPとTODOの双方に`/ai`へのリンクを置く**設計案**。TODO側はリンク追加に限定し、TODOのフォーム・API呼び出し・処理を変えない（R07）。 |
| `textarea` | 質問入力。2,000文字は**コードポイント**で数え、HTMLの`maxlength`を唯一の判定にしない。前後空白はサーバーで確定的に除去。 |
| `button[type=submit]` | 送信中は無効化。同一待機中の連打を抑止。 |
| `role=status`の表示 | `送信中...`、成功、履歴読み込み中などの進捗。 |
| `role=alert`の表示 | 入力エラー、APIエラー、DBエラー、タイムアウト、デモ停止。問い合わせIDは必要時のみ表示。**質問・回答・履歴・エラー文・問い合わせIDとも`textContent`またはテキストノードで描画**し、HTMLとして解釈しない。`error.code`に対応したフロント固定文言を優先する案。 |
| `answer`領域 | AI回答は**プレーンテキスト**。改行の表示はCSSを使いHTMLとして解釈しない。 |
| `history`一覧 | 作成日時・質問・回答を最新20件、指定順。0件表示。内容は`textContent`相当で描画する。 |
| `history-reload` | 履歴取得失敗時に利用者が明示して再取得する。自動リトライしない。 |

### 3.2 状態モデル

| 状態 | 画面の振る舞い | 遷移 |
| --- | --- | --- |
| 初期表示 | フォーム使用可、履歴欄は「読み込み中」。`GET history`を一度発行 | 履歴成功／0件／履歴失敗／停止 |
| 入力待ち | 入力可能。前後空白やコードポイント数を補助的にチェック | 送信操作 |
| 送信中 | `送信中...`、ボタン無効、同一画面の二重押下禁止 | 201／エラー／ブラウザ待機終了 |
| 201成功 | 新回答を表示し、履歴を**1回**再取得 | 履歴成功／0件／履歴失敗 |
| 履歴0件 | **HTTP 200、`body.success === true`、`Array.isArray(body.data)`が全て成立し、配列長が0のときだけ**「まだ履歴はありません」。 | 送信／明示的再取得 |
| 質問失敗 | エラーの原因と再操作可能状態を表示。質問文は維持 | 利用者の再送（自動は不可） |
| 履歴失敗 | 非JSON応答、認証画面へのリダイレクト、502、JSON解析失敗、`data`欠落・型不正、`success !== true`を**0件と扱わず**失敗表示。コードに対応する安全な固定表示文を優先する。 | 手動再取得 |
| タイムアウト | 「応答が確認できませんでした。保存済みの可能性があります」等、**未確定を成功／保存失敗と断定しない** | 手動履歴確認／再送判断 |
| DEMO_DISABLED | 質問・履歴の利用不可表示。自動再送なし | デモ許可された環境へ |

**待機終了後：** ブラウザ待機終了でボタンは再度有効になるが、サーバー処理が続いている可能性がある。利用者への注意喚起、履歴確認を推奨。サーバー側の冪等性キー・重複排除を標準課題に確定追加しない（OPEN-AI-04）。

## 4. API設計（DES-AI-004）

- ベースパス：`/api/ai`。JSON APIは`Cache-Control: no-store`、`Content-Type: application/json; charset=utf-8`。
- 公開用レスポンスは `success` と `data` または `error` の構造で統一する（**採用設計**）。
- 成功時データの`created_at`はISO 8601文字列。`id`はDBのBIGINT型を使うため、JSONの精度損失を避けて**10進文字列**として返す（採用設計）。**ブラウザはIDをNumberに変換せず文字列のまま保持・描画**し、2^53-1を超えるIDを用いたテストを実施する（R08）。

### 4.1 POST `/api/ai/ask`

| 項目 | 仕様 |
| --- | --- |
| 入力 | `Content-Type: application/json`、本文 `{ "question": "..." }` のオブジェクト。余分なフィールドの扱いは**無視する案**（乱用・ログ汚染防止のため実装時再検討）。 |
| 検証 | JSON構文、16KiB受信上限、型が文字列、`trim()`に準じた前後空白除去、`Array.from`相当で1〜2,000 Unicodeコードポイント。U+200B単独の扱いはOPEN-AI-09で決定。 |
| 成功 | AI回答取得→同一行へ質問・回答INSERT成功→**201**。 |
| 失敗 | AI生成失敗またはDB保存失敗なら201は返さない。秘密値・質問全文をログに記載しない。 |

**成功応答例（提案）**

```json
{
  "success": true,
  "data": {
    "id": "123",
    "question": "質問例",
    "answer": "回答例",
    "created_at": "2026-11-11T05:00:00.000Z"
  }
}
```

### 4.2 GET `/api/ai/history`

- 入力：クエリパラメータなし。認証・利用者単位フィルタなし（**デモの共有履歴**）。
- 成功：**200**、`data`は配列（0件でも`[]`）。常に新しい順、最大20件。
- DB障害：**0件成功へフォールバックしない**。

```json
{
  "success": true,
  "data": []
}
```

### 4.3 エラー応答（採用設計・実装後に検証）

```json
{
  "success": false,
  "error": {
    "code": "AI_UNAVAILABLE",
    "message": "AIの回答を取得できませんでした",
    "requestId": "example-request-id"
  }
}
```

| 事象 | HTTP | `error.code` | Gemini／DB呼出 | 補足 |
| --- | --- | --- | --- | --- |
| Content-Type不正、本文・`question`型不正 | 400 | `INVALID_BODY` | **0回／0回** | AI用の入力検証で拒否。 |
| JSON構文不正 | 400 | `INVALID_JSON` | **0回／0回** | パーサー段階で拒否。 |
| 圧縮等の未対応Content-Encoding | 415 | `UNSUPPORTED_CONTENT_ENCODING` | **0回／0回** | JSON解析前に拒否。**REQ-AI-F009の「質問入力不正」の下位ケース**。 |
| トリム後0または2,001以上 | 422 | `VALIDATION_ERROR` | **0回／0回** | 文字数はUnicodeコードポイント。 |
| JSON本文が16,384バイト超 | 413 | `REQUEST_TOO_LARGE` | **0回／0回** | 型・内容検証前のサイズ制限。 |
| Gemini API到達不能・不正応答・空回答 | 502 | `AI_UNAVAILABLE` | Gemini 1回以内／DB **0回** | SDK自動再試行なし。 |
| Gemini処理期限超過 | 504 | `AI_TIMEOUT` | Gemini 1回以内／DB **0回** | 中断・実期限は未確定。 |
| **DB INSERT失敗が確定** | **500** | **`SAVE_FAILED`** | Gemini 1回／DB INSERT試行あり | **§8.2の許可リストに属するSQLSTATEを、実行したINSERTに対するPostgreSQLのエラー応答として受け取った場合のみ**確定失敗と分類する。失敗応答にAI回答を含めない。 |
| **DB INSERT結果不明** | **503**（応答可能な場合） | **`SAVE_RESULT_UNKNOWN`** | Gemini 1回／DB INSERT試行あり | §8.2の許可リスト外（接続断08、サーバー停止57、資源不足53、SQLSTATEなし・未知コード等）。**画面の固定文言は「保存結果を確認できませんでした」**。未保存・失敗を断定しない。 |
| **履歴SELECT失敗** | 500／503（原因別） | **`HISTORY_UNAVAILABLE`** | Gemini **0回**／DB SELECT試行あり | `data: []`として返さない。 |
| Production・未許可デモ環境の質問・履歴 | **503** | **`DEMO_DISABLED`** | **0回／0回** | ゲートで拒否。 |
| AIルート未定義URL（デモ許可時） | 404 | `NOT_FOUND` | **0回／0回** | 停止時はゲートの503が優先。 |
| POSTに非対応メソッド（許可時） | 404 | `NOT_FOUND` | **0回／0回** | 本設計では404を採用。 |
| AI用の想定外例外 | 500 | `INTERNAL_SERVER_ERROR` | **発生段階による** | 内部スタック・秘密値を隠す。 |

**利用者向けメッセージ（RV-AI-04）：** `SAVE_FAILED`は「回答を保存できませんでした」、`SAVE_RESULT_UNKNOWN`は**「保存結果を確認できませんでした。再送前に履歴をご確認ください」**と表示する設計案とする。ブラウザ側の応答未達・タイムアウトも保存の成否を断定しない固定文言とする。画面はサーバーの任意の`message`ではなく、認識済み`error.code`に対応する固定文言を選び、`textContent`で描画する。履歴確認ができない場合は未確定のままとし、自動再送はしない。

`requestId`はデバッグ用の不透明ID。ログとレスポンスを対応付けるだけで、ユーザーID・秘密値・質問本文・APIキーは含めない。**§4.3のHTTPステータス・エラーコード・応答形式は本設計で確定済み**とし、実装・テストでの一致を確認する。**保存INSERTでは許可リストの確定失敗を500、その他の結果不明を503とする。** 履歴SELECT失敗の500/503は別途DB障害分類に従う。保存失敗／結果不明／履歴失敗は`error.code`で判別する。 DB障害による応答未達の場合はHTTPコード自体が取得できないこともある。

### 4.4 JSON境界の試験

**本文形状別の期待結果（本設計では `express.json()` の `strict: true` を前提とする）：**

| 本文（Content-Type: application/json） | 判定箇所 | HTTP／`error.code` | Gemini／DB |
| --- | --- | --- | --- |
| 空本文（0バイト） | Controllerで未定義の本文を拒否 | 400 `INVALID_BODY` | 0回／0回 |
| `null` | 厳格JSONパーサーで拒否 | 400 `INVALID_JSON` | 0回／0回 |
| `"text"` | 厳格JSONパーサーで拒否 | 400 `INVALID_JSON` | 0回／0回 |
| `[]` | パーサー通過後、Controllerが配列を拒否 | 400 `INVALID_BODY` | 0回／0回 |
| `{}` | Controllerで質問フィールド欠落を拒否 | 400 `INVALID_BODY` | 0回／0回 |
| `{"question":123}` | Controllerで質問の型不正を拒否 | 400 `INVALID_BODY` | 0回／0回 |

Controllerは**本文が未定義・null・配列でもプロパティ参照で例外にならない**よう、本文が非nullのプレーンなJSONオブジェクトであることを先に判定してから `question` を参照する（例：オプショナルチェーン等）。本文が構文的に有効かどうかと、アプリとして正しい形かどうかを分ける。**空本文のパーサー挙動は採用Express設定で実測し、上表の400となることを試験する。**

- **1〜2,000コードポイント**はトリム後にサーバーで検証し、`String.length`を使用しない。
- U+1F600（😀）を1,500個、2,000個、2,001個としたテストを**エスケープされていないUTF-8 JSON**で送信。1,500／2,000は16KiBを満たす。2,001は文字長不正。
- 16,384／16,385バイトは**妥当な質問の前後に半角スペースを付加**し、送信バイト列を調整してテストする。Content-Length等を信頼せず、Expressの制限実装で判定する。0・1・2,000・2,001コードポイント、全角スペースのみ、改行のみも検証。
- `express.json({ limit: 16384 })` 相当をAI APIだけに設定。JSONパーサーの過大本文エラーは**413**で返す採用設計（TODOの現行400とは独立）。**本設計案ではリクエストの圧縮JSONを受理しない**。`Content-Encoding`が`identity`以外（例：`gzip`、`br`）ならJSON解析前に415 `UNSUPPORTED_CONTENT_ENCODING`で拒否する。符号化を指定しない通常のUTF-8 JSONに対し**実際の受信本文16,384バイト**を適用する（R09）。採用した仕様への適合は実装後に検証する。

### 8.2 成功と失敗の境界

| 事象 | サーバーの確定状態 | 画面・保存の扱い |
| --- | --- | --- |
| Gemini失敗（保存前） | 保存未実行 | 502/504等、質問・回答行は追加しない。 |
| Gemini成功、INSERTが許可リストのSQLSTATEで拒否された | 保存失敗が確定 | **500 `SAVE_FAILED`**を返し、回答全文は含めない。1行INSERTで質問だけ／回答だけの部分行は生じない。**自動INSERT再実行は行わない**。 |
| Gemini成功、INSERT成功、201送信成功 | 保存成功 | 201と回答表示。履歴に存在する。 |
| INSERTコミット成功をサーバーが確認した後、HTTP応答が届かない | **サーバーでは保存成功確定、ブラウザは結果不明** | 画面は通信エラーを表示しても、履歴に存在し得る。履歴を手動で確認し、二重送信に注意。 |
| INSERT時のDB接続断等でコミット結果が判別できない | **サーバーでも保存結果不明** | 応答可能なら503 `SAVE_RESULT_UNKNOWN`。201を返さず、AI回答全文を含めず、**自動INSERT再試行なし**。応答が届かない場合もあり、独立した履歴/DB確認で調査。無条件に「未保存」と表示しない。 |
| ブラウザ45秒経過だがサーバー継続 | **ブラウザでは結果不明** | サーバーが後から保存する可能性。ブラウザで保存失敗を断定しない。履歴確認結果をテスト記録。 |
| 履歴再取得失敗 | 質問の201はすでに確定済み | 質問保存成功を取り消さない。履歴欄だけにエラー。 |

**判定規則（INSERT時の許可リスト方式・設計案）：** PostgreSQLから**当該INSERT文そのものに対する明示的なエラー応答**を受け取り、SQLSTATEの先頭2文字が `22`（データ例外）、`23`（整合性制約）、`42`（構文・アクセス規則、権限不足`42501`を含む）、`P0`（PL/pgSQLエラー、`P0001`を含む）である場合に限り、**500 `SAVE_FAILED`**とする。単一文のINSERTについて、DBが文を拒否したことを確定できるクラスに限定する。**SQLSTATEが付いていても、当該INSERTへのサーバー応答か判別できない場合は確定扱いしない。**

**それ以外はfail-safeで503 `SAVE_RESULT_UNKNOWN`（応答可能な場合）：** SQLSTATE `08`（接続例外）、`57`（停止等）、`53`（資源不足）、SQLSTATEがない通信エラー、未知のクラス、例外の発生段階が不明な場合を含む。リクエスト処理中に追加DB照会をして確定状態を確認することは**判定の前提としない**。ログに回答全文は残さず、失敗応答にもAI回答を含めない。**INSERTを自動再試行しない**。

**確認と未決の区分：** 許可リストは採用`pg`ドライバの実際のエラー形状を、テスト用DBでの`42501`（権限拒否）／`P0001`（トリガー例外）の故障注入により検証して確定する。ドライバの動作が想定と違えば不明側に倒して判定表を見直す。**DB側の確定状態の照合や後続の履歴調査はリクエスト終了後の事後調査**としてOPEN-AI-07へ記録し、リアルタイム判定の必要条件にはしない。履歴SELECT失敗は別コード`HISTORY_UNAVAILABLE`とする。

| 試験ID | 注入箇所・方法（提案） | 期待する分類と確認 |
| --- | --- | --- |

| `TEST-AI-N007-02` | INSERT結果は成功したが、ブラウザへのHTTP応答が届かない状況をスタブ等で再現する | ブラウザは結果不明を示し、履歴を後で取得すると保存済みになり得ることを確認。自動再送なし |

**注入の安全性と限界：** 共有デモDBに権限変更・トリガーを適用しない。独立したテスト用DB／トランザクション後の復旧手順を使用する。`02b`はプロキシやスタブで**応答喪失を模擬したこと**と、実DBでコミット済みだったかを分けて記録する。実ネットワークで「送信後・応答前」のタイミングを厳密に再現できるかは未検証であり、再現できない場合はスタブ試験と結合試験を区別して未実施と記録する。リクエスト中に追加DB照会を行って分類しない。ユニークな試験質問は観測用であり、永続的な重複防止機構ではない。問い合わせID・試験ID・SQLSTATEクラス・注入時点・HTTP結果・事後履歴状態を記録し、質問・回答本文や秘密値はログに残さない。

**未決：** リクエストIDをDBへ保存して再送を冪等化するか、処理中断をどこまで伝搬するかは**現要件の必須機能に勝手に追加しない**。OPEN-AI-04、OPEN-AI-07として設計判断を残す。

**デモ許可判定の設計提案（R03）：** **Productionは常時停止**を最優先し、許可環境についてはサーバー側の明示的なデモ許可フラグと環境種別を併用する。**Previewを示す環境変数だけでは保護済みと見なさず**、ホスティング側のアクセス制御の有効性をデプロイ設定と無権限URLアクセスで確認する。保護の状態をサーバーから安全に確証できない構成では**許可せずfail-closed**とし、デモ許可スイッチをONにしない。Previewの保護済みであることはホスティングのアクセス制御設定・無権限アクセス試験で確認する。具体的な環境変数名（例：`AI_DEMO_ENABLED`、`VERCEL_ENV`）や判定の信頼源は未確定で、**環境変数が単に`preview`であることだけを「保護済み」の根拠にしない**。

### Previewの未認証アクセス試験（RV-AI-02、OPEN-AI-06）

実際に採用する認証／アクセス制御方式は**未決**。運用担当が保護設定、許可済みデモフラグ、到達可能な全URL（カスタムドメイン・プラットフォーム既定URL・別名URLを含む）をデモ前に確認する。認証情報を持たない別ブラウザ／プライベートウィンドウと、認証Cookie・トークンを持たないHTTPクライアントを使用し、各到達経路で次を実施する。

1. 未認証で `POST /api/ai/ask` に有効なJSONを送信し、**成功201ではない**こと、Gemini呼出・INSERTがないことをテスト記録で確認する。
2. 未認証で `GET /api/ai/history` にアクセスし、**成功200で履歴が取得できないこと、共有質問・回答が一切漏れないこと**を本文とレスポンスヘッダー／リダイレクト先まで確認する。認証画面のHTML・302/303・401/403・ゲート503など実応答をそのまま記録する（未認証で必ず503とは決めない）。
3. 認証済みの許可されたPreview利用者についてのみ、両APIが期待どおり動くことを確認し、無権限試験との違いを記録する。認証状態はCookieだけでなく実際のアクセス制御の設定で確認する。

**合格条件：** すべての到達経路で未認証者が質問も履歴も利用できず、共有履歴が本文・キャッシュ・リダイレクト先等に露出しない。いずれか未確認・成功可能なら**fail-closedでデモ許可をしない**。テスト実施前に保護方式を採用した事実とは扱わない。検証結果は`TEST-AI-N006-01`（質問）・`TEST-AI-N006-02`（履歴）として記録する。

運用検証：`Production`の質問・履歴APIにアクセス→両方503/`DEMO_DISABLED`、GeminiやDBアクセスが**0回**であることを安全なテスト記録で確認。Previewは保護されていないURL・認証前ブラウザから成功できないことを確認。`/`・`/todo`が従来どおり動くことを確認。
