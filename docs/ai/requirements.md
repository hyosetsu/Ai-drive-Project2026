## 1. 背景・目的・利用者

### 1.1 背景・目的

既存アプリにはTOP・TODO等の機能がある。利用者がWeb画面に疑問・質問を入力し、サーバーが外部AI（LLM）から回答を取得して表示する機能を追加する。既存TODOと同様のレイヤー分離を踏襲し、既存機能の動作を維持する。

### 1.2 利用者

一般ユーザーおよび管理者（`request.md` に記載）。**ログインや利用者別管理を意味しない。** 利用者を識別する方式は本書で新設しない。

### 1.3 標準課題の対象範囲

- 質問の入力・送信・検証
- サーバーから外部AI APIへの質問送信、回答の取得と画面表示
- AI回答取得後のDB保存、および最新20件の履歴表示（履歴をAIへの文脈に利用しない）
- 入力不正、通信失敗、保存失敗等の適切な扱い
- APIキーの機密管理、公開環境の制御、既存TOP・TODO等への影響防止
- 正常系・異常系および既存機能の受入テスト

### 1.4 対象外（標準課題に含めない）

ログイン機能の新設、ユーザーごとの認証・権限管理、過去会話をAIに送信する会話記憶、Markdownレンダリング、ストリーミング応答、ProductionでのAI API公開運用。**ブラウザまたはSDKの自動再試行機能は実装しない**（REQ-AI-F010）。

## 2. 授業の共通条件（待機時間のみ参考値）

| 項目 | 共通条件・位置づけ |
| --- | --- |
| 質問 | 前後空白を除去した後の長さが**1〜2,000 Unicodeコードポイント** |
| JSON本文 | **16KiB（16,384バイト）**を受信上限とする |
| 履歴 | **最新20件**。作成日時の**降順**、同日時なら**IDの降順** |
| 保存成功 | **AI回答取得とDB保存の双方が完了してから**成功応答 |
| 会話文脈 | AIに送信するのは**今回の質問のみ**。過去履歴は送信しない |
| 再送 | **ブラウザとSDKの自動再試行はしない** |
| 公開 | **ローカルまたは保護済みPreview**でデモ。**Productionでは質問APIを停止（授業条件）し、今回の採用済み設計判断により履歴APIも停止** |
| 待機（参考値・未確定） | **AI30秒、ブラウザ45秒**を参考設定とする。**最終値は実行環境の検証後に確定**する（REQ-AI-N007、OPEN-AI-05）。 |

## 3. 機能要件（REQ-AI-Fxxx）

| 要件ID | 要件（何を満たすか） | 受入条件 |
| --- | --- | --- |
| **REQ-AI-F001** | 質問を入力しAI回答を確認できるWeb画面を提供し、送信中の状態を示し、同一処理の二重送信を防ぐ。 | 質問入力・回答表示領域が利用でき、送信開始からブラウザ側の成功・失敗・待機終了の判定まで送信中と分かる表示があり、その待機中に送信操作を重ねても追加の質問処理が開始されない。**ブラウザの待機終了後は利用者による手動再送を可能とし、サーバー側で先行処理が継続している場合の重複対策はOPEN-AI-04で決める。** |
| **REQ-AI-F002** | 入力した質問をサーバーへ送信できる。 | 有効な質問の送信操作後、サーバーがその質問を受信し処理を開始する。**テスト用のサーバーログ（秘密値を含まない）またはAI呼び出し直前の記録**で、受信・処理開始を確認できる。 |
| **REQ-AI-F003** | 質問の**前後の空白文字（全角スペースU+3000、改行などを含む）**を除去し、除去後の長さが**1〜2,000 Unicodeコードポイント**のものだけを受け付ける。UTF-16コード単位数とは区別する。 | **境界値：** サーバーで除去後の0・1・2,000・2,001コードポイントを確認し、0・2,001は拒否、1・2,000は他の条件を満たせば受理する。<br>**絵文字：** 試験には**U+1F600（😀）という補助面の単一コードポイントの絵文字**を使用する。1,500個（1,500コードポイント／3,000 UTF-16コード単位）と2,000個は受理、2,001個は拒否する。絵文字試験は**エスケープなしの生UTF-8でエンコードしたJSON**を使い、16KiBの本文上限も満たすことを確認する。<br>**空白：** 全角スペースのみの質問は拒否する。除去対象の空白文字の厳密な集合（ゼロ幅スペースU+200Bのみの質問を空とするかを含む）は詳細設計で定義する（OPEN-AI-09）。 |
| **REQ-AI-F004** | 受け付けた今回の質問について、サーバー側で外部AIから回答を取得する（会話文脈はREQ-AI-D006に準拠）。 | 外部AIの正常応答時に回答を取得できる。過去履歴を含めないことはREQ-AI-D006の受入条件で確認する。 |
| **REQ-AI-F005** | AI回答取得と質問・回答のDB保存が**両方完了してから**質問処理の成功を返す。保存失敗時に質問・回答が中途半端に残らない（REQ-AI-D005に準拠）。 | 両方成功した場合のみ成功応答。**DB保存失敗がサーバー側で確定したケース**では成功応答を返さず、履歴取得で当該処理の質問・回答が現れず、質問のみ・回答のみの部分保存がないことを確認する（REQ-AI-D005）。**ブラウザのタイムアウト等で保存結果が不明な場合**は、この失敗確定ケースと区別してOPEN-AI-07で扱う。 |
| **REQ-AI-F006** | 正常に処理されたAI回答を画面に表示する。 | 成功応答に含まれる回答を利用者が読める。 |
| **REQ-AI-F007** | 保存された質問・回答の履歴を最新20件まで表示する（取得・順序の詳細はREQ-AI-D003）。 | デモ許可時、21件以上および作成日時が同じ履歴を含む場合、表示件数と順序がREQ-AI-D003で確認した取得結果と一致する。**停止環境では履歴表示せず503を利用不可として表示**する。 |
| **REQ-AI-F008** | 履歴0件の場合でも正常な履歴表示を行う（データ側の判定はREQ-AI-D004）。 | **200かつ正常な空配列**のとき、エラー表示ではなく「履歴なし」と分かる表示になる。**DB障害、非JSON、データ形式不正、停止503を0件扱いにせず**REQ-AI-F009の失敗・利用不可表示になる。 |
| **REQ-AI-F009** | **質問入力不正、JSON本文16KiB超過、AI通信・応答失敗、タイムアウト、DB保存失敗、履歴取得失敗、機能停止（Production）**を区別し、利用者が失敗または利用不可を理解できるメッセージを示す。 | 列挙した**7区分**をそれぞれ再現し、成功・履歴0件と誤表示せず、区分を判別できる画面表示または利用不可表示を確認する。**16KiB超過はAPIへの直接送信、または画面入力を前後空白で水増しして再現**し、**リクエスト本文サイズ超過**として入力文字数不正と区別する。秘密値・内部例外の詳細を画面・エラー応答に出さない（REQ-AI-N002、N004）。**保存結果不明は「DB保存失敗」区分の下位、ブラウザ待機終了は「タイムアウト」区分の下位、未対応Content-Encodingは「質問入力不正」区分の下位として扱い、結果不明時は保存失敗を断定しない。** |
| **REQ-AI-F010** | ブラウザ・AI SDKの自動再試行機能を使わない。利用者による明示的な再送操作のみを別の送信として扱う。 | **ブラウザ側に自動再試行の処理を実装していないこと**をコードで確認し、**AI SDK側の最大再試行回数が0に設定されていること**を確認する。通信失敗・タイムアウト・AI側失敗時に**1回の操作から自動再送されない**ことを通信記録等で確認する。送信中の二重操作はREQ-AI-F001で検証する。 |
| **REQ-AI-F011** | Productionでは標準課題のAI**質問APIと履歴取得APIの両方を停止**し、利用者へ機能停止・利用不可を示す。 | Productionで**質問・履歴両API**が503 `DEMO_DISABLED`を返し、Gemini呼出・DB保存・履歴SELECTとも**0回**。利用者へ利用不可を示す（REQ-AI-F009、OPEN-AI-06採用決定）。 |
| **REQ-AI-F012** | 入力不正や外部サービス障害が起きても、既存Webアプリが継続動作する。 | AI機能の異常後も、既存TOP・TODOおよび既存エラー処理が期待どおりに動作する。 |

## 4. 非機能要件（REQ-AI-Nxxx）

| 要件ID | 要件（何を満たすか） | 受入条件 |
| --- | --- | --- |
| **REQ-AI-N001** | 既存TODOの設計パターンに倣い、AI機能の**Router / Controller / Model・Service**の責務を分離する。 | ルーティング、入力受付・応答制御、AI連携、DBアクセスの責務が構成上区別でき、既存の共通処理を不必要に重複・破壊していない。 |
| **REQ-AI-N002** | APIキー等の機密情報をソースコード・画面・正常応答・エラー応答に露出させず、**`dotenv` を利用して環境変数から読み込む**。 | コード・設定方針・画面・応答を点検し、秘密値の直書きや出力がなく、`dotenv` 経由の環境変数による読み込み方針が確認できる。秘密値は文書や検証結果に記載しない。 |
| **REQ-AI-N003** | JSON本文の受信上限を16,384バイトとする。 | **16,384バイト**の適正なJSON本文は他の入力条件を満たせば受け付け、**16,385バイト**のJSON本文は拒否することをサーバー側で確認する。**再現方法：有効な質問の前後に半角空白を付け、除去後の質問が有効なままJSON本文を指定のバイト数に調整する**（具体的な試験データは試験設計で確定）。質問のコードポイント数とJSON本文のバイト数を混同しない。絵文字試験の文字種・符号化・境界値は**REQ-AI-F003**を参照する。 |
| **REQ-AI-N004** | 例外を適切に扱い、**共通グローバルエラーハンドラーが既存にない場合はAI専用エラー処理で代替**し、既存の404・例外時の応答と秘密情報の非露出を維持する。 | AI専用の最終エラー処理が想定外の例外を安全な500に変換し、**既存のTOP・TODO・未知URLの404・エラー応答を変更しない**。スタックトレース、内部例外本文、APIキー等が画面・HTTP応答・限定ログに出ないことを確認する。全体ハンドラーを後日追加する場合は既存応答を変更前後で比較し、別途承認する。 |
| **REQ-AI-N005** | 既存のTOP・TODO・共通ルーティング・DB接続を維持する。 | AI機能追加後に既存機能の正常系・異常系の回帰テストが通る。 |
| **REQ-AI-N006** | 標準デモはローカルまたは**アクセス制御されたPreview**だけで行い、未保護のアクセスからAI質問API・履歴取得APIのいずれも利用させない。 | Previewの保護設定を確認したうえ、**保護を通らないURLアクセス（未認証・未保護の経路）では質問・履歴取得の両APIが成功応答せず、共有履歴も開示されない**ことを実アクセスで確認する。保護方式はOPEN-AI-06で決める。**無権限の別ブラウザ／HTTPクライアントから、到達可能な各URLの質問POSTと履歴GETをそれぞれ検証し、保護方式が未決・未検証の場合はデモを許可しない。** |
| **REQ-AI-N007** | **参考値**のAI30秒・ブラウザ45秒を検証し、実行環境に合わせて最終の待機時間を確定する。 | 実行環境でタイムアウトを発生させ、REQ-AI-F009の失敗表示とREQ-AI-F010の自動再試行なしを確認し、**ブラウザ側のタイムアウト後に履歴を取得して保存結果を確認し、画面の失敗表示とDB保存状態の一致・不一致を含めて**採用値・検証結果を記録する。**30秒・45秒は未確定の参考値**（OPEN-AI-05）。 |
| **REQ-AI-N008** | 正常系・異常系と既存機能への影響を検証し、結果を記録する。 | テスト内容・期待結果・実結果が `docs/ai/04_test_results.md` 等で追跡できる。 |

## 5. データ要件（REQ-AI-Dxxx）

| 要件ID | 要件（何を満たすか） | 受入条件 |
| --- | --- | --- |
| **REQ-AI-D001** | 成功した質問処理に対応する質問テキストとAI回答をDBに保持する。 | 成功応答後に、対応する質問・回答がDBから取得できる。 |
| **REQ-AI-D002** | 保存履歴を一意に識別でき、作成日時とIDで安定して並び替えられる。 | 各履歴に識別子と作成日時が存在し、同日時でもID降順で表示順を決定できる。 |
| **REQ-AI-D003** | 履歴一覧は作成日時の降順、同日時はIDの降順で最大20件を取得する。 | 21件以上および同一作成日時を含む試験データで、期待どおりの20件と順序を取得できる。**DBの物理保持上限ではない**（OPEN-AI-03）。 |
| **REQ-AI-D004** | 履歴が存在しない状態を正常な0件として扱い、DB障害と区別する。 | 履歴なしの場合は正常な0件を返す。DB障害を再現した場合には0件を返さず、履歴取得失敗としてREQ-AI-F009の表示につながる。 |
| **REQ-AI-D005** | AI回答取得後のDB保存に失敗した処理は成功にせず、**質問だけ・回答だけが残る部分保存を防ぐ**。 | **制御可能なDB保存障害**を再現して失敗応答を受けた後、履歴取得に当該質問・回答が現れず、DB上にも質問のみ・回答のみの中途半端な状態がないことを確認する。**ブラウザ側のタイムアウト等で保存結果が不明なケース**では、本項の「DB保存失敗が確定したケース」と同じ結果を保証できるとは限らないため、OPEN-AI-07で扱いを決める。 |
| **REQ-AI-D006** | 過去の保存履歴を新たなAI質問の会話文脈に含めない。 | 履歴に既存データがある場合でも、**AI APIへの入力を検査するテスト用スタブまたは秘密値を含まない検証記録**により、過去の質問・回答が送信されず、利用者の質問として今回分だけが含まれると確認できる。**固定のシステムプロンプト（回答方針）を併用できるか、その許容範囲は詳細設計で決定する**（OPEN-AI-01）。 |

> **履歴件数の解釈：** 「最新20件」は**取得・表示件数の上限（確定）**であり、**DB保持件数の上限（未決）ではない**。DBに20件を超えて保存する場合の保持・削除方針は共通条件から確定できないため、詳細設計前に決める（OPEN-AI-03）。

## 6. 必須の振る舞いと境界条件

| ケース | 必須の振る舞い・検証観点 | 対応要件 |
| --- | --- | --- |
| 前後空白の除去・全角スペースのみ／改行のみ | 前後の空白を除去し、空白のみなら0コードポイントとして拒否 | F003, F009 |
| 質問が1／2,000コードポイント | 他の条件を満たせば受理（前後の全角空白や改行を含む場合も検証） | F003 |
| 質問が0／2,001コードポイント | 拒否しAI呼び出し・DB保存を行わない | F003, F009 |
| 絵文字入りの質問 | **REQ-AI-F003の絵文字に関する受入条件**を適用する（試験文字種・境界値・送信形式は同要件を正とする） | F003 |
| JSON本文が16,384バイト | 有効な質問の前後を空白で調整した適正なJSONで、他の入力条件を満たせば受理 | N003 |
| JSON本文が16,385バイト | 前後空白を使う等してAPI直接送信で再現し、本文サイズ超過として拒否。質問文字数不正とは区別して表示 | N003, F009 |
| 送信直後から結果確定まで | 送信中と分かる表示をし、二重押下で同一処理を追加起動しない | F001 |
| 有効な質問の送信 | 秘密値を含まない記録等でサーバー受信と処理開始を確認 | F002 |
| AI回答取得・DB保存の両方成功 | 成功応答を返し回答を表示し、質問・回答を履歴取得できる | F004, F005, F006, D001 |
| AI回答取得後にDB保存失敗 | 成功を返さない。**保存失敗が確定**した場合、失敗応答後の履歴取得で該当質問・回答が現れず、部分保存がない | F005, D005, F009 |
| 履歴0件 | 正常な0件と表示する | F008, D004 |
| 履歴取得中のDB障害 | 履歴0件と扱わず、履歴取得失敗を表示する | F009, D004 |
| 履歴21件以上／同日時の履歴 | 最新20件を作成日時降順・同日時ID降順で取得・表示 | F007, D003 |
| AI通信・応答失敗 | 成功扱いせず、失敗の区分が分かる表示。自動再試行しない | F009, F010 |
| AI／ブラウザのタイムアウト | タイムアウト失敗を表示し、自動再試行しない。ブラウザの待機終了後、履歴を確認して保存結果を記録。具体値は環境検証後に確定 | F009, F010, N007, OPEN-AI-07 |
| ProductionでAI質問・履歴APIにアクセス | 両APIで503 `DEMO_DISABLED`。Gemini呼出・DB保存・履歴取得を行わず利用不可を示す | F007, F008, F009, F011 |
| Preview保護を通らないURL経路 | 未認証の別ブラウザ／HTTPクライアントで質問POST・履歴GETを各URLから試験し、両APIの成功応答も共有履歴の開示もないことを確認。未検証ならデモ不可 | N006 |
| 想定外の例外／存在しないURL | **既存の404・例外時の応答（Express既定）を変更せず**、AI専用エラー処理でAI側の例外を扱う。秘密値・スタックトレースを応答に露出しない | N002, N004, F012 |

※ **F001はブラウザが応答を待っている間の連続押下防止を扱う。ブラウザの待機終了（タイムアウトを含む）後は手動再送可能とし、先行するサーバー処理との重複への対応はOPEN-AI-04で決定する。**

※ **停止時の503 `DEMO_DISABLED`はOPEN-AI-06で採用済み**。その他のHTTPステータスコード・エラー応答形式も`spec.md` §4.3の**採用設計として確定**し、実装・試験で適合を確認する。失敗時の入力保持、手動再送時の重複対策は引き続きOPEN-AI-04で決める。**質問長とJSON本文サイズは別々の制約**である。**ブラウザ側タイムアウトなど保存結果が不明な通信障害**はOPEN-AI-07で扱い、**サーバー側でDB保存失敗が確定した場合**の受入条件を緩めない。

### 未決事項と確定事項の区別

- **確定**：本書2章の**待機を除く7項目**、原本 `request.md` に書かれた基本機能・レイヤー分離・秘密情報管理・既存機能保護。**今回の追加設計判断としてProductionの履歴取得停止を採用済み**。**待機30秒／45秒は授業提示の参考値であり、最終設定は実測後に確定**する。
- **採用済み設計判断**：AI提供元はGemini、専用画面`/ai`（`public/ai/index.html`・`public/ai/app.js`）、`spec.md` §4.3のHTTPステータス・エラー応答形式、Productionでの質問・履歴両API停止。DB列などの詳細構成は`spec.md`を正とする。
- **提案・未確定／実環境検証事項**：Gemini SDK・バージョン・モデルID・環境変数名、固定システムプロンプト、画面の細部・導線の見た目、履歴の物理保持上限と削除方針、担当者割当、具体的なタイムアウト値、Preview保護の具体的方式、API利用上限・コスト対策、故障注入によるSQLSTATE判定の妥当性。
- **追加しない**：ログイン、過去会話をAIに送る会話記憶、Markdown表示等。
